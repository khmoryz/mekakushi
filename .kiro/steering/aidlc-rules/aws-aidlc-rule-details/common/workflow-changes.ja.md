# ワークフロー途中の変更とフェーズ管理

## 概要

ユーザーはワークフロー中に実行計画やフェーズ実行の変更を要求することがあります。このドキュメントは、これらの要求を安全かつ効果的に処理するためのガイダンスを提供します。

---

## ワークフロー途中の変更の種類

### 1. スキップされたフェーズの追加

**シナリオ**: ユーザーが元々スキップされたフェーズを追加したい場合

**例**: 「やはり、スキップしたユーザーストーリーのステージを追加したい」

**対応**:
1. **リクエストの確認**: 「ユーザーストーリーのステージを追加したいのですね。これにより、ユーザーストーリーとペルソナが作成されます。よろしいですか？」
2. **依存関係の確認**: すべての前提条件となるフェーズが完了していることを確認します。
3. **実行計画の更新**: `execution-plan.md` に根拠とともにフェーズを追加します。
4. **状態の更新**: `aidlc-state.md` でフェーズを「PENDING」とマークします。
5. **フェーズの実行**: 通常のフェーズ実行プロセスに従います。
6. **変更の記録**: `audit.md` にタイムスタンプと理由を文書化します。

**考慮事項**:
- 新しい成果物から利益を得られる可能性のある後のフェーズを更新する必要があるかもしれません。
- 既存の成果物は、新しい情報を組み込むために修正が必要になる場合があります。
- タイムラインが延長されます。

---

### 2. 計画されたフェーズのスキップ

**シナリオ**: ユーザーが実行予定だったフェーズをスキップしたい場合

**例**: 「NFR設計ステージは今のところスキップしましょう」

**対応**:
1. **リクエストの確認**: 「NFR設計をスキップしたいのですね。これは、NFRパターンや論理コンポーネントが組み込まれないことを意味します。よろしいですか？」
2. **影響の警告**: 何が欠落し、潜在的な結果がどうなるかを説明します。
3. **明示的な確認の取得**: ユーザーは影響を理解したことを明示的に確認する必要があります。
4. **実行計画の更新**: 理由とともにフェーズを「SKIPPED」とマークします。
5. **状態の更新**: `aidlc-state.md` でフェーズを「SKIPPED」とマークします。
6. **後のフェーズの調整**: 後のフェーズで手動セットアップが必要になる可能性があることを注記します。
7. **変更の記録**: `audit.md` にタイムスタンプと理由を文書化します。

**考慮事項**:
- 後のフェーズが失敗したり、手動介入が必要になる場合があります。
- ユーザーは欠落した成果物に対する責任を受け入れます。
- 必要であれば後で追加できます。

---

### 3. 現在のステージの再開

**シナリオ**: ユーザーが現在のステージの結果に不満で、やり直したい場合

**例**: 「このユーザーストーリーは気に入らない。最初からやり直せますか？」

**対応**:
1. **懸念の理解**: 「ストーリーについて具体的に何を変更したいですか？」
2. **選択肢の提示**:
   - **選択肢A**: 既存の成果物を修正する（高速で、一部の作業を保持）
   - **選択肢B**: 完全に再開する（クリーンな状態で、より多くの時間が必要）
3. **再開が選択された場合**:
   - 既存の成果物をアーカイブする: `{artifact}.backup.{timestamp}`
   - 計画ファイル内のステージのチェックボックスをリセットする
   - `aidlc-state.md` でステージを「IN PROGRESS」とマークする
   - ステージの完了ステータスをクリアする
   - 最初から再実行する
4. **変更の記録**: 再開の理由と何が変更されるかを文書化します。

**考慮事項**:
- 既存の作業は失われます（ただしバックアップされます）。
- 依存するステージをやり直す必要がある場合があります。
- タイムラインが延長されます。

---

### 4. 前のステージの再開

**シナリオ**: ユーザーが完了したステージに戻ってやり直したい場合

**例**: 「以前に行ったアーキテクチャの決定を変更したい」

**対応**:
1. **影響の評価**: 再開するステージに依存するすべてのステージを特定します。
2. **ユーザーへの警告**: 「アプリケーション設計を再開すると、ユニット計画、ユニット生成、全ユニットのユニットごと設計、コード計画、コード生成をやり直す必要があります。よろしいですか？」
3. **明示的な確認の取得**: ユーザーは完全な影響を理解する必要があります。
4. **確認された場合**:
   - 影響を受けるすべての成果物をアーカイブする
   - `aidlc-state.md` ですべての影響を受けるステージをリセットする
   - すべての影響を受ける計画ファイルのチェックボックスをクリアする
   - 再開するステージに戻る
   - その時点から再実行する
5. **変更の記録**: 完全な影響と再開の理由を文書化します。

**考慮事項**:
- 大幅な手戻りが必要です。
- すべての依存ステージをやり直す必要があります。
- タイムラインが大幅に延長されます。
- 再開よりも修正の方が良い場合を検討します。

---

### 5. ステージの深さの変更

**シナリオ**: ユーザーが現在または次のステージの深さレベルを変更したい場合

**例**: 「標準ではなく、包括的な要件分析をしましょう」

**対応**:
1. **リクエストの確認**: 「要件分析を標準から包括的な深さに変更したいのですね。これはより徹底的になりますが、時間がかかります。よろしいですか？」
2. **実行計画の更新**: `workflow-planning.md` で深さレベルを変更します。
3. **アプローチの調整**: ステージの包括的な深さのガイドラインに従います。
4. **見積もりの更新**: 新しいタイムラインの見積もりをユーザーに通知します。
5. **変更の記録**: 深さの変更と理由を文書化します。

**考慮事項**:
- 深さが大きいほど時間はかかるが品質は向上します。
- 深さが小さいほど高速ですが、詳細を見逃す可能性があります。
- ステージの完了後ではなく、前または中にのみ変更できます。

---

### 6. ワークフローの一時停止

**シナリオ**: ユーザーが一時停止して後で再開する必要がある場合

**例**: 「今は中断して、明日続けたい」

**対応**:
1. **現在のステップの完了**: 可能であれば進行中の現在のステップを完了します。
2. **チェックボックスの更新**: すべての完了したステップを `[x]` でマークします。
3. **状態の更新**: `aidlc-state.md` が現在のステータスを反映していることを確認します。
4. **一時停止の記録**: `audit.md` に一時停止点を文書化します。
5. **再開手順の提供**: 「戻ってきたら、既存のプロジェクトを検出し、[現在のフェーズ、現在のステップ]から続行することを提案します」

**再開時**:
1. **既存プロジェクトの検出**: `aidlc-state.md` を確認します。
2. **コンテキストの読み込み**: 完了したステージからすべての成果物を読み込みます。
3. **ステータスの表示**: 現在のステージと次のステップを表示します。
4. **選択肢の提示**: 中断したところから続けるか、前の作業を確認するか。
5. **再開の記録**: `audit.md` に再開点を文書化します。

---

### 7. アーキテクチャ決定の変更

**シナリオ**: ユーザーがモノリスからマイクロサービス（またはその逆）に変更したい場合

**例**: 「やはり、モノリスではなくマイクロサービスにしましょう」

**対応**:
1. **現在の進捗の評価**: ワークフローのどこまで進んでいるかを判断します。
2. **影響の説明**:
   - ユニット計画前の場合: 最小限の影響、決定を更新するだけ。
   - ユニット計画後の場合: ユニット計画、ユニット生成、すべてのユニットごと設計をやり直す必要があります。
   - コード生成後の場合: 大幅な手戻りが必要です。
3. **アプローチの推奨**:
   - ワークフローの早い段階: アプリケーション設計ステージから再開します。
   - ワークフローの遅い段階: 再開に対する修正の実現可能性を検討します。
4. **確認の取得**: ユーザーは変更の完全な範囲を理解する必要があります。
5. **変更の実行**: 影響を受けるステージの再開手順に従います。

**考慮事項**:
- アーキテクチャの変更は連鎖的な影響を及ぼします。
- ワークフローの早い段階ほど変更は容易です。
- ワークフローの遅い段階では、コストと利益を比較検討します。

---

### 8. ユニットの追加/削除

**シナリオ**: ユーザーがユニット生成後にユニットを追加または削除したい場合

**例**: 「支払いユニットを支払いと請求に分割する必要があります」

**対応**:
1. **影響の評価**: どのユニットの設計/コードが完了しているかを判断します。
2. **結果の説明**:
   - ユニットの追加: 新しいユニットの完全な設計とコードが必要です。
   - ユニットの削除: 機能を他のユニットに再配分する必要があります。
   - ユニットの分割: 両方の結果ユニットの設計とコードをやり直す必要があります。
3. **ユニット成果物の更新**:
   - `unit-of-work.md` を修正します。
   - `unit-of-work-dependency.md` を更新します。
   - `unit-of-work-story-map.md` を改訂します。
4. **影響を受けるユニットのリセット**: 影響を受けるユニットを再設計が必要とマークします。
5. **変更の実行**: 影響を受けるユニットの通常のユニット設計とコードプロセスに従います。

**考慮事項**:
- それらのユニットのすべての下流ステージに影響します。
- 依存関係が変更されると、他のユニットに影響を与える可能性があります。
- タイムラインへの影響は、影響を受けるユニットの数によって異なります。

---

## 変更処理の一般ガイドライン

### 変更前

1. **リクエストの理解**: ユーザーが何を変更したいのか、なぜ変更したいのかについて明確化の質問をします。
2. **影響の評価**: 影響を受けるすべてのステージ、成果物、依存関係を特定します。
3. **結果の説明**: 何をやり直す必要があるか、タイムラインへの影響を明確に伝えます。
4. **代替案の提示**: 再開よりも修正の方が良い場合があります。
5. **明示的な確認の取得**: ユーザーは影響を理解し、受け入れる必要があります。

### 変更中

1. **既存作業のアーカイブ**: 破壊的な変更を行う前に必ずバックアップします。
2. **すべての追跡の更新**: `aidlc-state.md`、計画ファイル、`audit.md` を同期させ続けます。
3. **進捗の伝達**: 何が起こっているかをユーザーに知らせ続けます。
4. **変更の検証**: すべての成果物で変更が一貫していることを確認します。
5. **継続性のテスト**: 変更後もワークフローがスムーズに続行できることを確認します。

### 変更後

1. **一貫性の検証**: すべての成果物が変更と整合していることを確認します。
2. **ドキュメントの更新**: すべての参照が更新されていることを確認します。
3. **完全な記録**: `audit.md` に完全な変更履歴を文書化します。
4. **ユーザーとの確認**: 変更がユーザーの期待を満たしていることを確認します。
5. **ワークフローの再開**: 新しい状態から通常の実行を続行します。

## 変更リクエストのデシジョンツリー

```
ユーザーが変更をリクエスト
    |
    ├─ 現在のフェーズか？
    |   ├─ はい: 現在のフェーズを修正または再開できる
    |   └─ いいえ: 次の質問へ
    |
    ├─ 完了したフェーズか？
    |   ├─ はい: 依存フェーズへの影響を評価
    |   |   ├─ 低影響: 修正して依存関係を更新
    |   |   └─ 高影響: そのフェーズからの再開を推奨
    |   └─ いいえ: 次の質問へ
    |
    ├─ スキップされたフェーズの追加か？
    |   ├─ はい: 前提条件を確認し、計画に追加して実行
    |   └─ いいえ: 次の質問へ
    |
    ├─ 計画されたフェーズのスキップか？
    |   ├─ はい: 影響を警告し、確認を得てスキップ
    |   └─ いいえ: 次の質問へ
    |
    └─ 深さレベルの変更か？
        ├─ はい: 計画を更新し、アプローチを調整
        └─ いいえ: ユーザーにリクエストを明確化してもらう
```

```markdown

**リクエスト**: [ユーザーが変更したい内容]
**現在の状態**: [ワークフローの現在地]
**影響評価**: [影響を受けるもの]
**ユーザーの確認**: [ユーザーの明示的な確認]
**実行されたアクション**: [何が行われたか]
**影響を受けた成果物**: [変更/リセットされたファイルのリスト]

---
```

## ベストプラクティス

1. **常に確認**: ユーザーの明示的な確認なしに破壊的な変更を行わない。
2. **影響の説明**: 決定する前にユーザーが結果を理解する必要がある。
3. **選択肢の提示**: 変更を処理する方法が複数ある場合がある。
4. **最初にアーカイブ**: 破壊的な変更を行う前に必ずバックアップする。
5. **すべてを更新**: すべての追跡ファイルを同期させ続ける。
6. **徹底的な記録**: 監査証跡のためにすべての変更を文書化する。
7. **後に検証**: ワークフローがスムーズに続行できることを確認する。
8. **柔軟であること**: ワークフローは厳格なプロセスを強制するのではなく、ユーザーのニーズに適応すべきである。
